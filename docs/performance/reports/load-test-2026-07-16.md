| Профиль | Вердикт | Комментарий |

## 5. Где не соответствуем (подсветка)

1. **Error rate под нагрузкой** — главный gap к §6 P1 и tactical &gt;95%: при ramp 5→30 VU visual отдаёт 502/503; mixed error **26.8%** при цели **&lt;1%**.
2. **Ёмкость с logo в mix** — плановый peak ~7 RPS достижим по throughput, но **не с SLA по ошибкам** (§6 P3).
3. **Продуктовые SLA ТЗ** — не валидированы (нет full query / Stage 1–2).
4. **Наблюдаемость (P6)** — нет time-series CPU/RAM/RPS из Prometheus за прогон.
5. **Целевое железо A100** — бизнес предполагает GPU; CPU-стенд занижает capacity visual и не закрывает MoSCoW M12 как среду приёмки.

---

## 6. Анализ: что нужно исправить

### Приоритет 1 — разблокировать peak с error &lt; 1%

1. Ограничить concurrency `visual-model-service` (очередь / semaphore / worker pool); отдавать осмысленный **503** и сделать retry/backoff на backend.
2. Исключить reload embeddings / рестарт engine mid-load (в логах stress наблюдалась перезагрузка модели).
3. Вынести visual на больший CPU/GPU или отдельный инстанс; поднять лимиты контейнера (сейчас 2 vCPU / ~4 GiB на весь стек).
4. Повторить профиль **peak** (15 VU / ~7 RPS) и отдельно **S2-only** capacity, пока error rate &lt; 1%.

### Приоритет 2 — закрыть gap к бизнесу

1. Поднять Prometheus + Grafana на стенде **до** следующего прогона (критерий P6).
2. После появления S5/S8 добавить E2E timing: full query &lt; 2 мин, Stage 1 P95/P99, Stage 2 ≤ 120 с (Gate 2).
3. Зафиксировать **измеренную** устойчивую ёмкость (макс. RPS при error &lt; 1%) в `load_testing_goals.md` и на дашборде Load Testing.

### Приоритет 3 — процесс

1. Не считать smoke/baseline = соответствие продуктовому SLA.
2. Документировать каждый прогон по §6 PASS/FAIL (этот отчёт — образец).
3. Для релизной приёмки планировать прогон на **A100** (MoSCoW M12), не только на CPU VPS.

---

## 7. Рекомендуемый следующий шаг

1. Починить concurrency/стабильность visual.
2. Поднять monitoring stack.
3. Прогон: `peak` (target ~7 RPS) + `S2-only` ramp → зафиксировать max RPS при error &lt; 1%.
4. Обновить цели ёмкости и закрыть issue по capacity.
